# MERIDIAN-9 プロジェクト 全体設計＆マイルストーン

## 1. プロジェクト概要

**プロジェクト名**：MERIDIAN-9 / Project JANUS（コードネーム：`mrd9_janus`）
**ジャンル**：エクストラクション型 PvE ミッション（ルートシューター系）
**プラットフォーム**：FiveM（ESX または QBCore 連携、Standalone 動作も可能な設計）
**プレイ人数**：1〜5 名／セッション、複数セッション並行可能
**1 セッション想定時間**：10〜30 分
**開発体制想定**：1〜2 名、期間 6〜8 週間

## 2. システム全体アーキテクチャ

### 2.1 コンポーネント構成

システムは大きく 4 層に分かれます。**外部リソース層**として The Apocalypse Project（マップ）、Multiverse-World-Manager（バケット基盤）、TP-Advanced-Zombies 改（敵 AI）を利用。**コアロジック層**として本体スクリプト `mrd9_janus` がセッション管理・ミッション進行・報酬計算を担当。**UI 層**として NUI で HUD・対話・パーティ編成・査定画面を実装。**データ永続化層**として oxmysql で契約者情報・統計・ランキングを保存。

### 2.2 リソース間の関係

```
[mrd9_janus] (本体)
    ├─ [multiverse_manager] を内部関数として利用（バケット発行）
    ├─ [tp_zombies_lite] にイベント発火（ゾンビアリーナ起動）
    ├─ [apocalypse_project] のマップ座標を参照
    ├─ [ox_lib] でメニュー・通知
    ├─ [ox_target] で NPC インタラクション
    └─ [oxmysql] でデータ永続化
```

## 3. データフロー設計

### 3.1 ゲームループの状態遷移

プレイヤーは次の 6 状態を遷移します。**IDLE**（通常ロスサントス、バケット 0）→ **DIALOGUE**（ヴェガと対話中）→ **PARTY_FORMING**（パーティ編成 UI 表示中）→ **TRANSITIONING**（フェード演出中、バケット切替）→ **IN_MISSION**（サイト・ナイン内、独自バケット）→ **EXTRACTING**（脱出処理中）→ **IDLE**（帰還、報酬付与）。死亡時は IN_MISSION から直接 IDLE へ強制遷移し、所持品は全ロスト。

### 3.2 サーバー側データ構造

セッション管理の中心となるデータ構造を以下のように設計します。

```lua
-- セッションオブジェクト
Session = {
    id = "S_1234567890",
    bucket = 101,                    -- ユニークなバケット番号
    leader = playerSrc,
    members = { src1, src2, src3 },
    state = "IN_MISSION",            -- FORMING/TRANSITIONING/IN_MISSION/ENDING
    startedAt = timestamp,
    endsAt = timestamp + timeLimit,
    mission = {
        type = "SAMPLE_RECOVERY",
        difficulty = "NORMAL",
        targetMap = "site_nine_main",
    },
    inventory = {
        [src1] = { {id, name, rarity, value}, ... },
        [src2] = { ... },
    },
    zombieState = {
        currentWave = 2,
        totalKilled = 47,
    },
    aliveCount = 3,
}

-- 契約者DB（永続化）
Contract = {
    identifier = "license:xxx",
    signedAt = timestamp,
    totalMissions = 12,
    totalExtracts = 8,
    totalDeaths = 4,
    totalEarnings = 145000,
    bestExtractValue = 25000,
}
```

### 3.3 クライアント・サーバー間イベント設計

主要なネットイベントを整理します。**クライアント→サーバー**は `mrd9:requestDialogue`（対話開始）、`mrd9:signContract`（契約締結）、`mrd9:requestStartMission`（ミッション開始要求）、`mrd9:respondPartyInvite`（招待承諾／拒否）、`mrd9:requestExtract`（脱出要求）、`mrd9:lootItem`（アイテム取得）、`mrd9:playerDied`（死亡通知）。**サーバー→クライアント**は `mrd9:onDialogueData`（対話データ送信）、`mrd9:onPartyInvite`（招待通知）、`mrd9:onMissionStart`（ミッション開始）、`mrd9:onTransition`（フェード演出）、`mrd9:onMissionEnd`（ミッション終了・結果）、`mrd9:onHudUpdate`（HUD 更新）。

セキュリティ観点で、**全ての判定（脱出位置、アイテム取得距離、死亡確認）はサーバー側で再検証**し、クライアントを信用しない設計にします。

## 4. 機能仕様（最小実装スコープ）

### 4.1 必須機能（MVP）

最初のリリースに含める機能を明確化します。**ヴェガ NPC スポーンと対話**（ox_target ベース、初回／リピート分岐）、**契約締結と DB 登録**（oxmysql）、**パーティ編成**（1〜5 名、招待→承諾フロー）、**バケット発行とサイト・ナインへの転送**（Multiverse 連携、フェード演出）、**ゾンビスポーン**（TP 改、固定 3 ウェーブ）、**アイテムスポーン**（10〜20 固定座標からランダム選出、3 レアリティ）、**HUD 表示**（自分のHP大、メンバーHP小、タイマー、所持品数）、**脱出ポイント表示と脱出処理**（マップに 2 箇所、近接で起動）、**死亡時の全ロスト処理**、**帰還後の自動査定と報酬振り込み**、**サーバールール文書（守秘義務）の表示**。

### 4.2 第二段階機能（MVP 後）

需要を見て追加する機能。複数ミッションタイプ（観測機器設置、生存者救出など）、難易度選択（Easy/Normal/Hard）、装備持ち込みシステム、保険システム、トレーダー NPC（個別売買）、ロアアイテム閲覧、ランキングボード、Subject-0 ボス戦、観戦モード、ボイス範囲制限連携（pma-voice）。

### 4.3 対象外（実装しない）

サーバー全体ゾンビ化、PvP モード、複雑な経済シミュレーション、フルクラフトシステム——これらは MERIDIAN-9 のコンセプトから外れるか、別 MOD で実現すべき領域なので含めません。

## 5. UI/UX 設計

### 5.1 主要 UI 画面

**対話画面**は画面下部にヴェガのバストアップ（小）＋テキスト枠＋選択肢ボタン、AMBIENT な暗いトーン。**契約書画面**は中央に契約書ドキュメント風 UI、スクロール可能、最下部に「サイン」ボタン（マウスで署名アニメーション）。**パーティ編成画面**は左に近隣の契約済みプレイヤーリスト、右に現在のパーティメンバー、招待ボタン。**HUD（ミッション中）**は左上に自分の HP バー（大、320×40px）、左中央にメンバー HP（小、200×24px 縦並び）、右上に経過時間とウェーブ情報、右下に所持品数＋推定価値。**査定画面**はミッション帰還時に表示、回収物一覧→個別価値→合計額→振り込み完了アニメーション。

### 5.2 デザイントンマナ

MERIDIAN-9 ロゴに合わせ、**ダークネイビー（#0A1628）背景＋シルバー（#C8D0DC）テキスト＋アクセントブルー（#3DA8E8）**で統一。フォントは英数字に Inter または Roboto Mono、日本語に Noto Sans JP。**冷たく、科学的で、無機質**な印象を全画面で維持。エフェクトは控えめで、過度な派手さは避けます。

### 5.3 演出（フェード・パーティクル）

ゲート起動時の演出として、地下室の床に青いパーティクル（`scr_rcbarry2` 系）→画面青フェード（3 秒）→真っ白フラッシュ→サイト・ナインで起動、というシーケンス。脱出時は逆順で、サイト・ナインで真っ白フラッシュ→青フェード→地下室で覚醒。これらは `effects.lua` に集約。

## 6. データベース設計

oxmysql 前提で、最小限のテーブル構成。

```sql
-- 契約者テーブル
CREATE TABLE mrd9_contracts (
    identifier VARCHAR(64) PRIMARY KEY,
    signed_at DATETIME NOT NULL,
    status ENUM('active', 'suspended', 'terminated') DEFAULT 'active',
    notes TEXT
);

-- 統計テーブル
CREATE TABLE mrd9_stats (
    identifier VARCHAR(64) PRIMARY KEY,
    total_missions INT DEFAULT 0,
    total_extracts INT DEFAULT 0,
    total_deaths INT DEFAULT 0,
    total_earnings BIGINT DEFAULT 0,
    best_extract_value INT DEFAULT 0,
    fastest_extract_seconds INT DEFAULT NULL,
    last_mission_at DATETIME,
    FOREIGN KEY (identifier) REFERENCES mrd9_contracts(identifier)
);

-- ミッション履歴テーブル（任意、ランキング用）
CREATE TABLE mrd9_mission_logs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    session_id VARCHAR(32) NOT NULL,
    identifier VARCHAR(64) NOT NULL,
    started_at DATETIME NOT NULL,
    ended_at DATETIME,
    outcome ENUM('extracted', 'died', 'timeout', 'aborted'),
    items_recovered_json JSON,
    earnings INT DEFAULT 0,
    INDEX idx_identifier (identifier),
    INDEX idx_session (session_id)
);
```

## 7. マイルストーン（6〜8 週間想定）

## 8. リスク管理と懸念事項

### 8.1 技術的リスク

**TP-Advanced-Zombies のサポート終了**——既知のバグや FiveM アップデートへの非対応リスクあり。対策として、改造時に最低限のコードのみ抽出し、不要部分は削除して保守性を上げる。最悪の場合、`WeponzTV/Standalone-Zombie-System` への切り替え準備。

**OneSync 同期問題**——ルーティングバケット内のエンティティ同期に稀に不整合が出ることがある。対策として、重要なエンティティ（ゾンビ・アイテム）はサーバー側で生成し、定期的に存在確認。

**The Apocalypse Project の重さ**——ストリーミング量が多く、低スペックプレイヤーの読み込み遅延の可能性。対策として、最初のミッションエリアを限定し、必要部分のみストリーミングする調整。

### 8.2 設計的リスク

**バケット枯渇**——FiveM のバケット番号は 0〜2^32-1 だが、同時セッション数が増えると管理が複雑化。対策として、終了したセッションのバケット番号を再利用するプール管理。

**パーティ離脱時の挙動**——ミッション中に誰かが切断した場合の処理。対策として、切断＝死亡扱いで所持品ロスト、サーバー側で正しく検知し残りメンバーには通知。

**アイテム複製エクスプロイト**——クライアントを信用するとアイテム取得を多重発火される可能性。対策として、サーバー側で取得済みフラグを管理し、同一アイテムの二重取得を拒否。

### 8.3 運用的リスク

**RP 整合性の崩壊**——プレイヤーがゲーム内で「ゾンビがいた」と公言してしまう。対策として、サーバールール明文化＋ヴェガのセリフで毎回守秘義務を強調＋違反時の運営介入ルール策定。

**プレイヤーの想定外行動**——契約済みでない人を無理やり連れて行こうとする等。対策として、未契約者は物理的にゲート起動不可、地下扉を契約者のみ通過可能に。

## 9. 成功指標（KPI）

リリース後の評価基準を設定しておきます。**プレイ頻度**として週あたりの総セッション数、**継続率**として契約者の 2 回目以降参加率、**完走率**として脱出成功 vs 死亡比率、**バランス指標**として平均報酬額・平均所持時間、**RP 浸透度**として街中での自発的言及数（運営観察）。これらをログから自動集計できる管理画面を Milestone 10 で簡易実装すると、運営判断がしやすくなります。

## 修正・追加検討ポイント

このマイルストーン案について、特に確認・調整したい点を挙げます。

**(A) スコープの妥当性**：MVP 機能リストは多すぎ／少なすぎないか。「これは最初は不要」「これは絶対欲しい」があれば教えてください。

**(B) 期間の妥当性**：6〜8 週間という見積もりは、想定されている開発体制・時間と合っているか。短くしたい／長くてもよい、どちらでしょうか。

**(C) フレームワーク選定**：ESX か QBCore か Standalone か——既存サーバーの環境次第で大きく実装が変わります。

**(D) マイルストーン順序**：「先に演出を見たい」「先にゾンビ戦を試したい」など、心理的なモチベ維持のため順序変更を希望される場合は調整可能。

**(E) サーバー導入規模**：プライベートで少人数で遊ぶのか、公開サーバーで多数プレイヤーが利用するのか——スケール想定によってデータベース設計や負荷対策の重み付けが変わります。

修正点・追加要望をいただければ、それに合わせて全体設計を更新します。
